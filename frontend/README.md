# Long Horizon dashboard

A Next.js dashboard for the 311 memory pipeline in `docs/implementation-plan.md`.

## Start

```sh
cd frontend
npm install
npm run dev
```

Open http://localhost:3000. Node 20.9+ is required. The initial screen contains a checked-in snapshot generated by the actual deterministic in-memory harness from `fixtures/311-small.json`; it makes no Atlas or model calls. The same template recommendation appears in both response cards because that is what the adapter actually returns.

**Run replay** invokes the Python harness again, processing both modes in separate stores with the same chronological batches. From the repository root, install the Python project into your preferred environment. The frontend uses `.venv-memory/bin/python` if present, otherwise `python3`; override with `DASHBOARD_PYTHON` in `frontend/.env.local`.

```sh
python3 -m venv .venv-memory
.venv-memory/bin/pip install -e .
```

The replay endpoint requires a Node server with Python and the repository available. It is intended for local development; a Node-only/serverless deployment can display the bundled replay and use live HTTP comparisons, but cannot regenerate the Python replay.

## Connect the live API

Copy `.env.example` to `.env.local` and set:

```dotenv
MEMORY_API_URL=http://127.0.0.1:8000
MEMORY_API_TOKEN=
OPENROUTER_API_KEY=your-key
OPENROUTER_MODEL=anthropic/claude-haiku-4.5
```

Restart Next.js. Credentials are read only on the server. The root project's `.env` is not automatically loaded by Next.js. `MEMORY_API_TOKEN` is optional for a local API, but should match the Fly secret of the same name in production.

The merged conversation API in `backend/api.py` is storage-injected. A local Atlas-backed startup example, run from the repository root:

```sh
.venv-memory/bin/python - <<'PY'
import os
from backend.atlas import _load_env
from backend.api import MemoryApiService, serve
from backend.memory.conversation import MongoConversationStore
from backend.memory.embeddings import AtlasMemorySearch
from backend.memory.retrieval_adapter import MongoMemoryRetrievalStore
from backend.memory.store import MongoMemoryStore

os.environ.update(_load_env())
store = MongoMemoryStore.from_env()
conversations = MongoConversationStore(store.database['short_term_events'])
conversations.ensure_indexes()
search = AtlasMemorySearch.from_env(store.nodes)
retrieval = MongoMemoryRetrievalStore(store, search)
serve(MemoryApiService(conversations, retrieval), host='127.0.0.1', port=8000)
PY
```

This requires the existing Atlas environment settings, graph data and a ready vector index. It does not create or populate the long-term memory graph; use the project's ingestion/harness commands for that.

Choose **Response evaluation → New comparison**. The server calls:

| Method | Endpoint                                             | Purpose                                      |
| ------ | ---------------------------------------------------- | -------------------------------------------- |
| GET    | `/v1/sessions/{session_id}/messages?limit=20`        | Read recent history before adding the prompt |
| POST   | `/v1/sessions/{session_id}/turns`                    | Store the prompt with an idempotency key     |
| POST   | `/v1/sessions/{session_id}/turns/{turn_id}/context`  | Retrieve bounded graph context               |
| POST   | `/v1/sessions/{session_id}/turns/{turn_id}/response` | Store the generated response                 |

The normal response is stored in `{session_id}.baseline`. Both model calls use the same current prompt, recent history, model, temperature (0), and output cap (700 tokens). Only retrieved long-term memory differs. These are per-turn comparisons sharing the memory session's history; they are not isolated longitudinal baseline experiments. Model calls execute in parallel. Live results show the returned context graph, not the whole Atlas graph. Failed comparisons retain the previous visible result and display an error; partial upstream writes can exist if a later request fails.

## What the UI reports

- **Overview:** ordered ingestion → historical retrieval → extraction → merge → Louvain grouping → recommendation; inspect individual batches and event payloads.
- **Memory explorer:** actual graph nodes/edges with a bounded schematic view, summary and retrieved-seed filters, source drill-down, and searchable original records in replay mode.
- **Response evaluation:** actual response text, supplied source IDs, provider token usage and model latency. Source counts describe available evidence, not independently verified citation quality. Replay token/latency values are unmeasured.
- **Event trace:** actual harness events. The conversation API does not expose pipeline traces or grouping results, so these are explicitly unavailable in live mode.
- **Export run:** download the complete displayed run as JSON.

Answer quality is not automatically scored. Complaint recurrence requires matched seven-day observed windows and does not establish the causal effectiveness of an unexecuted intervention. No synthetic quality score or causal improvement claim is shown.

Navigation is preserved in `?view=overview|memory|evaluation|events`. Filters and node selections are local to the view. Dialogs support Escape and keyboard focus; reduced motion and mobile layouts are supported.

## Verification

```sh
npm run typecheck
npm test
npm run build
npx playwright install chromium
# With npm run dev running in another terminal:
npm run test:e2e
```

From the repository root:

```sh
.venv-memory/bin/python -m pytest -q
.venv-memory/bin/python -m scripts.dashboard_snapshot --output frontend/lib/replay.json
```

The frontend tests exercise the endpoint contract, controlled model inputs, upstream errors, invalid payloads, navigation, graph/source inspection, mobile overflow and real local Python replay.
